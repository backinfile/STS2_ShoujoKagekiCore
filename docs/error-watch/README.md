# 玩家报错每日巡检

本仓库统一维护 Karen、官方 Core 与 Junna 的报错巡检。每天北京时间 09:00 执行；本聊天的最新安排和已记录的人工处理结论优先。

## 入口与范围

每次先读本仓库 `AGENTS.md`、本文件和以下资料：

- `artifacts/error-watch/config.json`：只读 API、时区、待修复文档、监控仓库和已授权修复交接。
- `artifacts/error-watch/state.json`：成功基线、观察计数、指纹映射与官方公告基线。
- `artifacts/error-watch/triage-policy.json`：人工归属、忽略／搁置、修复范围和发布核验结论。
- `docs/待修复问题.md`，以及监控仓库的 `AGENTS.md` 和相关最新修复记录。

Karen、Core、Junna 均为自有 Mod。Core 当前 ID 为 `ShoujoKagekiCore`，历史 ID `ShoujoKagekiAijoCore` 的记录归于同一仓库，沿用稳定问题编号。旧 Karen 包内的公共实现按当前源码归属 Core。

例行巡检直接维护本仓库的文档和已忽略本地状态。源码修复、游戏测试、部署、发版、Git 提交推送及新增修复任务分派由用户另行安排。沿用 UTF-8、最小改动和最小必要验证。

## 先核对官方游戏版本

先访问《Slay the Spire 2》官方 Steam 公告或官方新闻 API（appid `2868840`），分别核对正式版主分支与 `public-beta` 的更新、热修复和回滚。审阅新公告及无版本号标题，不能只比较版本数字。

记录公告标题／标识、分支、版本、北京时间、来源链接和检查时间，与上次成功公告基线比较。新公告涉及 Mod 加载、接口／ABI、选牌、序列化、联机或资源加载时，核对三者当前 Runtime 择版、真实游戏引用与实际支持范围。公告版本、玩家版本、本地快照和发行包分别判断；适配风险没有具体失败证据时记为待核验。

原始公告保存在忽略目录，摘要写入待修复文档。公告检查与全量错误采集分别推进成功基线。公告失败时保留上次成功记录，注明无法确认版本和重试范围，继续可完成的巡检。

## 完整采集与增量比较

使用只读采集器生成本轮证据文件。采集器先尝试轻量清单快照，逐页读取，按指纹补抓新增或变化的详情。旧服务沿用全量列表，单并发采集并遵守 `Retry-After`。成功基线由巡检分析完成后更新。

```powershell
python tools/telemetry/read_error_inventory.py --config artifacts/error-watch/config.json --baseline artifacts/error-watch/state.json --output artifacts/error-watch/<本轮目录>/collection.json
```

以指纹、累计次数、会话数、首次／最近时间和版本判断新增或变化，为相关条目读取完整详情、调用栈和启用 Mod 清单。Core、Junna 版本从 `core_telemetry` 与新旧 ID 的 `mods` 清单读取；旧协议 `mod_version` 仅用于 Karen。缺少版本记为未知。

抓取期间新增数据时按指纹合并分页，保留更大的已观察次数、会话数与最近时间，以及更早的首次时间。历史补报可能不在最近窗口，必要时合并 `recent`、`count`、`sessions` 排序补齐。完整采集、详情读取和分析成功后才推进全量成功基线。

同时核对 `total`、`group_limit`、`stored_reports`、`report_limit` 和覆盖状态。容量受限或恢复时，写入巡检记录与本地状态。

## 归属与处理约定

收录本系列自身的具体失败点、三者直接兼容边界，以及有定向证据确认归属的功能异常。按异常类型、核心调用链和触发场景合并同一根因，避免按版本或 Mod 组合重复建项。

以下记录标为“忽略，不处理”，保留原因并更新观察计数：

- 其他 Mod、BaseLib／RitsuLib 自身异常，且没有本系列具体兼容边界证据。
- 无本系列具体失败点或定向归属证据的通用引擎、动作取消与生命周期告警。
- 开发探针、测试样例及普通诊断输出。

角色卡名、公共序列化字段、卡池条目、启用清单和通用 Harmony／异步包装不足以判定归属。MCP 在启用清单中也不足以排除正常玩法中的实际缺陷。出现当前已合入代码的具体失败点或正常流程同链证据时，重新审阅并写明变化原因；旧忽略记录可作为关联证据保留。

与系列外第三方 Mod 的兼容不足，后续修复任务中能以小范围改动处理并完成必要验证的就处理；无法简单处理的标“搁置”，注明具体兼容对象、依据和原因。Core 是公共依赖或归属未明均不是搁置理由。次数增长不自动恢复忽略或搁置项。

## 修复交接与发布核验

每次核对 `repair_handoffs` 中全部已授权任务的 `result_file`／`result_files`、归属仓库任务记录、可核验提交和交付包。旧档案按配置中的源码／档案仓库定位。同步修复状态不依赖本轮错误全量采集成功。

- 任务未完成：修复中。
- 源码完成但尚未获准合并：待合并。
- 已合并未发布：待上线／原包核验。
- 有发布回执、实时元数据及对应交付证据：已发布，待原组合核验。

本地构建、版本号相同或 Git 合入都不能单独证明实现已上线。核对实际 DLL／包哈希、来源提交、客户端重启与服务端部署状态。Core 随 Karen 内嵌包发布时，明确发布渠道，独立 Core 和 Junna 的状态分别核验。新旧 Core ID 的发行策略以当前源码和实际包为准。

按子范围保留已合并修复和原组合未完成项，不能用整体任务完成覆盖未修复范围。已修复条目同链再出现时先核对版本和包身份；新增实际证据优先于旧状态摘要。保留人工备注、原状态、修复提交、验证及发布历史。

## 文档、证据与失败处理

有效条目记录稳定编号、归属仓库、优先级、状态、摘要、游戏和相关 Mod 版本、平台、首次／最近北京时间、上报次数、单指纹会话数、关键栈／指纹和下一步。跨指纹会话数不能直接相加为玩家数。

更新文档检查时间和简短巡检记录。原始响应、完整栈、Mod 版本清单、审阅映射和去重状态保存在已忽略的 `artifacts/error-watch/`。文档使用仓库相对路径、外部仓库用途占位符和脱敏摘要；私有地址、凭据、个人路径与玩家信息留在忽略目录。

访问失败、分页缺失或详情异常时保留原成功计数基线，记录失败原因与待重试范围。公告及修复交接已独立核验成功的状态可照常同步。

运行结果概括新增可处理问题、明显增长／状态变化、文档更新和失败情况。没有实质变化或仍不可处理时保持静默，按当前 heartbeat 约定返回结果。
