# 后台修复计划

先让日常巡检与页面读取、玩家上传并行运行，再解决归档恢复和长期容量，最后处理工作台。验收以故障复现和单项改动的结果为准。生产压测、部署、容量策略变更和正式清理按各自范围另行确认。依据见 [后台代码审阅](README.md)。

## 1. 限制巡检开销并保护前台请求

1. 在现有巡检入口把旧列表扫描和详情补抓的并发先各降到 1，按错误类型退避并遵守 `Retry-After`。能力探测发现当前服务支持轻量清单时，按游标顺序获取清单，仅补抓新增或有变化的指纹详情。完整性核验成功后更新巡检基线，异常时保留上一次成功记录。 [巡检约定](../../error-watch/README.md)
2. 为交互读取、巡检与重报表、玩家上传分配并发额度，保留总上限。入口应在慢查询排队之前判断是否还有额度，过载时发送完整的 HTTP `503` 和短 `Retry-After`。保留现有按请求频率限流的 `429` 和存储容量的 `507`。在代理和服务端记录固定路由类别、状态、耗时、运行中和拒绝数。 [HTTP 服务](../../../services/telemetry/app.py#L679) · [Nginx 部署配置](../../../deploy/telemetry/install.py#L146)
3. 在生产库副本上验证仓库已有的 `inventory=1`。以约 20,000 个指纹为基准，500 条一页，约 40 次清单请求。按源站观测到的上报节奏，在翻页期间加入新指纹、计数更新和重复重试，核对是否能稳定完成。若全局修订号反复使扫描重来，增加短期固定快照，后续游标绑定同一修订，设置快照数量、大小和有效期上限。响应明确标记过期，并沿用已有清单协议供旧巡检读取。 [清单实现](../../../services/telemetry/error_retention.py#L197)

**验收。** 隔离环境同时运行完整巡检、普通页面读取和测试上报。全量指纹应无缺失、无重复，计数与同一修订匹配。正常混合负载下，页面和有效上传均成功，常用列表的 P95 初始目标为 2 秒。刻意填满巡检额度时，巡检收到 503，页面和上传仍可成功。用同一份库、相同 CPU 配额记录前后请求数、延迟和拒绝数。

## 2. 补齐迁移与发布回退

1. 安装器在切换前生成候选配置并校验，记录程序链接、服务环境、Nginx 配置、systemd 单元和定时器状态。迁移先在一致的生产库副本上运行，记录耗时、额外磁盘占用、旧记录与去重校验结果。 [安装器](../../../deploy/telemetry/install.py) · [发布说明](../../../deploy/telemetry/README.md)
2. 把程序切换、服务启动、代理重载和业务验证纳入同一次发布。`/healthz` 验证存活，额外核对受保护的页面、报错列表、清单协议，以及隔离库中的代表性上传和重试。正式报错清理通过独立步骤启用，先验证策略导入和 dry-run 的候选名单。
3. 在隔离部署中分别模拟配置校验、启动和业务验证失败，确认原入口恢复。迁移后的数据库与旧程序兼容时，可回退程序和配置并保留写入。需要恢复数据库时，先保留切换后的数据，再按演练过的恢复路径处理这一时段新增的报告和对局。

**验收。** 正常发布后页面、上传和巡检入口可用。失败演练能恢复程序、配置及定时器状态。新旧协议、已有指纹计数、归档索引和重复上传的行为与发布前一致。

## 3. 修复原始归档的恢复和容量

1. 将 SQLite 备份和对应的原始文件清单作为同一恢复点。恢复工具先校验现有备份和压缩包清单，能为归档前的旧备份找回已经迁入压缩包的原始请求。按 SHA256 和原始长度核对，每个备份只恢复其已有对局引用。 [原始归档](../../../services/telemetry/raw_archive.py) · [读取和归档切换](../../../services/telemetry/app.py#L569)
2. 将原始归档额度按实际保留的文件字节计量。同一个压缩包只计一次，松散文件及在途压缩包需要预留空间。对比逻辑原始字节、实际占用和剩余额度的指标，给归档、数据库、活动报错类别和报告数各自预警。维护命令报告孤立文件，回收和冷归档步骤按确认的保留期限执行。 [现有额度判断](../../../services/telemetry/app.py#L342) · [报错容量](../../../services/telemetry/error_reports.py#L213)

**验收。** 从归档前和归档后的备份分别恢复到空目录，核对历史查询、原始 JSON 的 SHA256 和重复上传。用小额度验证压缩后可继续收新的对局，真实达到容量上限才返回 507。演练归档中断和重试，确认原始文件可校验、可复用。

## 4. 优化普通查询与维护任务

1. 根据路由耗时先处理重复计算。报错列表的全局筛选项和对局视图的筛选元数据按实际依赖复用。缓存按数据版本或短有效期失效，保留原响应字段和筛选语义。全时段卡牌统计先采样，达到延迟瓶颈后再减少逐局解析或加入预聚合。 [对局读取](../../../services/telemetry/app.py#L444) · [报错读取](../../../services/telemetry/error_reports.py#L294)
2. 记录上传、归档索引更新与报错清理的写锁耗时。有证据表明写锁等待影响请求时，先将可在事务外完成的对局编码和压缩前移，再核对归档文件与索引提交的顺序。 [上传事务](../../../services/telemetry/app.py#L355) · [清理事务](../../../services/telemetry/error_retention.py#L125)

**验收。** 同一份数据上比较常用筛选和全时段报表的计数及 P95。检查早期放弃、多人席位、未知语言和旧格式字段。上传和归档交错运行时，重试幂等、原始文件校验和统计口径一致。

## 5. 独立修复工作台

1. 网关按路由尽早执行大小限制。图片沿用 16 MiB 限额，流式转发并在客户端中断时终止转发。限制大包并发，分别返回输入错误、上游超时和连接中断。 [网关](../../../tools/workbench/deploy/relay.cjs) · [MCP 请求处理](../../../tools/workbench/mcp-daemon.cjs)
2. 为每个可编辑工作区的 SQLite 和共享资产生成同批次恢复清单，核对版本、历史、回执和资产哈希。公开发布合并短时间连续变更，验证新 `current` 后保留当前与一个可回退快照，再按确认的范围清旧发布目录。共享资产回收另按全工作区引用核对。 [公开快照发布](../../../tools/workbench/deploy/publish-readonly.cjs) · [工作区存储](../../../tools/workbench/mcp-sqlite.cjs)

**验收。** 上传允许大小的图片时，小型 MCP 查询仍可用。超限、断流和上传重试有对应响应与可核对记录。四个公开工作区均可读取现行快照，旧快照能回切。把各编辑库和共享资产恢复到隔离目录后，核对历史、版本、可见图片和相同 `requestId` 的重放行为。

## 交付顺序

- 第一批提交覆盖第 1、2 阶段。巡检单并发可以先按现有运维入口调整。服务端与巡检端各有回退点。生产切换在混合负载与迁移回退演练通过后进行。
- 第二批提交覆盖第 3 阶段。先完成成套恢复验证，再调整归档容量记账。保留期限和清理动作单独批准。
- 第 4、5 阶段分别提交。查询优化按测量结果拆分，工作台可与遥测后续阶段并行。

实现时只自动运行对应改动的最小定向验证。完整混合负载、生产库副本恢复演练及部署确认按批次提交验证范围和结果。
