## 原因追查

本体开战逐张复制永久牌到抽牌堆。源牌的闪耀余量小于等于 0，或已经标为耗尽时，Core 将普通复制替换为空壳。永久牌若仍留在牌组，每场战斗都会重新生成一个空壳。这条路径与附件连续两场的表现吻合。日志只记录打出了空壳，没有源牌实例或复制时的闪耀状态，无法确认原局具体在哪一步损坏了余量或牌组。[扣次和永久来源](../../../src/Modules/Shine/ShineService.cs#L184) · [复制](../../../src/Modules/Shine/ShineService.cs#L385)

- 核对 Android 启动指纹与下载的正式工坊包一致。Core 2.0.3 包含已在 1.9.8 修复的关闭父批次漏归档问题。旧修复在结算时生效，读取现存零余量永久牌时不改写牌组。附件起点是续玩，开局进程的具体包无法由这份日志核定。[旧批次修复](../fix-shine-batch-20261120/README.md)
- BaseLib 的玩家 JSON 扩展在 Android 日志里报错。Core 随后正常加载，续玩时耗尽堆为 8，终局原始记录仍有 8 张。既往同版工坊包在禁用玩家 JSON 扩展后完成两轮写盘与重启，永久牌 2/7 的预算与耗尽档案正常保留。现有证据未把 BaseLib 的异常连到这局的空壳。[存档验证](../shine-exhaust-resume/README.md)
- 第 19 层偷窃草蜢移除并归还的是原有《信封》实例。该层另获一张《水分补充》，它已经出现在耗尽档案。《迈向那个舞台》仍在两场战斗中正常打出。《出场》是尚待核对的永久来源候选。第 23 层取得的这张牌一直留到终局，两场日志均未出现它的出牌记录，原始余量未上传。

## 后续代码审查与报错

1. 闪耀扣到 0 时先写入永久来源，随后批次收尾才归档并移牌。归档序列化、档案变更订阅和耗尽表现位于移牌的 `finally` 之前。即使已经进入 `finally`，移除战斗副本失败也会挡住后面的永久牌移除。隔离游戏中使用真实《出场》，让档案变更订阅抛错，复现永久原牌停在 0/6、原异常向外传播、原生复制生成空壳、保存检查点写入残留。原局附件没有这个调用栈，且终局档案没有《出场》，故该复现确认的是一条可触发路径。[归档和移牌顺序](../../../src/Modules/Shine/ShineService.cs#L306)
2. 旧档兼容分支把任一 Core 闪耀整数字段视为新版输入。若只有上限，余量沿用模型反序列化前的状态。带闪耀属性的《出场》在桌面负向对照里获得默认 6/6。没有默认闪耀的牌可停在负哨兵，随后被复制为空壳。[字段分支](../../../src/Modules/Shine/ShineService.cs#L437)
3. 扣次和归档对永久来源的判断存在差异。前者依照非临时与 `DeckVersion` 回写，后者还要求不是 dupe，而且永久来源仍属于持有者的牌组。v0.113.0 原生普通临时复制会清除 `DeckVersion`。其他共享路径是否曾提供不一致的来源尚无现场证据。[预算回写](../../../src/Modules/Shine/ShineService.cs#L195)

新增 `[shine/deck.cleanup]`、`[shine/deck.checkpoint]`、`[shine/deck.restore]` 和 `[shine/deck.shell]` 报错。仅观察出现在永久牌组里的异常状态，包括耗尽残留、存档计数字段缺失和已进入永久牌组的空壳。每张运行时牌在同一阶段报告一次。报错记录模型 ID、角色、楼层、遭遇、相关卡牌状态、可见的最后一次归零写入、保存字段及异常类型和调用栈。玩家账号、种子与完整存档不进入这类报错。归档中卡牌的正常临时复制继续按既有规则生成空壳。

报错沿用 Core 上传开关、队列、限流和后台既有协议。调查只索引原局现有日志和后台数据。新增探针放在忽略目录，故障注入与修改存档只针对隔离游戏。玩法和原生存档写入保持原有行为。
